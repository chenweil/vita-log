# 06.1-04a: 本人登录失败的四类语义

**What to build:** 把 `EditorAuth.unlock(): boolean` 改为能区分「成功 / 凭据被拒 / 被限流 / 服务不可用」的结果，让页面分别提示。本票源自 #06.1-04 复审时如实记录的已知边界——`/api/login` 返回 503 时页面会说「账号或密码错误」，把本人送去重打一遍不可能有用的密码。

**Blocked by:** 06.1-04

**Status:** done

- [x] `unlock()` 返回可区分的结果类型，`boolean` 契约作废；`ReadOnlyEditorAuth` 同步。
- [x] 凭据被拒时提示服务端原文；限流时提示「稍后重试」；服务不可用时**不得**出现「账号或密码错误」。
- [x] 分类依据是 **HTTP 状态**，不是响应体里的 `code`（401 与 429 共用 `code: unauthorized`）。
- [x] 网络失败、以及 200 但响应体无法识别的情形，归入「服务不可用」而不是「凭据错误」。
- [x] D1 与 SQLite 两种后端都验证 401、429、503/网络失败；不得只在一个模式上测。
- [x] 变异验证覆盖每一类分类。

### 为什么这一条不能算「文案小事」

503 与 401 给出的是**相反的修复动作**：一个要让本人稍后重试，一个要让本人检查密码。旧契约把两者压成同一个 `false`，页面只能显示「账号或密码错误」——于是服务故障时，本人得到的第一条指令是去改一样没问题的东西。更糟的是它把**没有信息**也报成了**确定的坏消息**：网络断了、响应体坏了、`/api/session` 探测失败，全都是同一个 `catch { return false }`。页面于是对一个它一无所知的失败，给出了一个具体但错误的诊断。

顺带一个易错点：两个后端在限流时都返回 `code: 'unauthorized'`（`server/api.ts:50` 与 `functions/api/session.ts:57`），只有 HTTP 状态是 429。按 `code` 分类会把限流重新并回凭据错误。

### 两侧 503 的来源都��真实的

- D1 侧：`SqliteD1({ failOn: /INSERT INTO owner_session/ })` 让 `openSession` 抛 `SessionStoreError`，经 `functions/api/session.ts:105` 的 `guard` 转成真 503。读取仍正常，所以页面已经打开——失败的是「登录」这一步，而不是整个服务。
- SQLite 侧：页面打开后把 store 的数据库关掉，凭据校验读不到行，经 `server/api.ts:84` 的兜底转成真 503。

两条都走各自后端自己的错误路径，替身（`createApi(store)` 直接作传输层）**不决定任何状态码**。

### 集成测试钉的是什么，单元测试钉的是什么（这里先前有一句不实的注释）

页面只渲染 `result.message`。两个真实后端都自带 message，于是**页面级用例对「outcome 分类错了」是不敏感的**——实测把 503 改判成 `rejected` 或按 `body.code` 分类，两个集成套件都全绿。真正被钉住的是：

- **集成层**：每个后端的真实响应到达页面后，本人看到的是该看到的文字。某个后端改了状态码或文案，这里会红。
- **单元层**（`tests/auth.test.ts`）：分类本身，尤其是**服务端没给 message 时**——一条限流若被归类成凭据错误，落到页面上就是那句「账号或密码错误」，正是本票要消灭的缺陷。

初版的 D1 限流用例注释写着「这也钉住了页面按状态而非 code 分类」，那是**不实的**，已改正。

### 变异验证

8 个变异体，全部转红：

| 变异 | 结果 |
| --- | --- |
| 限流被归类为凭据错误 | 红（2 处） |
| 所有失败都归为凭据错误（回到旧契约） | 红（3 处） |
| 丢弃服务端原文，改用客户端默认文案 | 红（2 处） |
| 页面无视结果，仍用固定的「账号或密码错误」 | 红（6 处） |
| 网络失败被归为凭据错误 | 红（4 处） |
| 只读部署谎称凭据被拒 | 红（补测后） |
| 200 但响应体读不出 deadline 时仍报「已解锁」 | 红（补测后） |
| `rejected` 的默认文案改成服务不可用 | 红（补测后） |

**两次「变异后仍绿」都指向没人会走到的分支，处理方式相反。**

`ReadOnlyEditorAuth.unlock()` 在产品里不可达（只读构建不渲染解锁控件），初版用例只断言「outcome 不是 unlocked」——把它换成**本票要消灭的那个旧缺陷**（`rejected` + 「账号或密码错误」），全量仍然全绿。补的断言钉的是实质：**只读部署从不评估密码，因此绝不能对密码有意见**。

另一处是 `DEFAULT_MESSAGES.rejected`：初版只给 `limited` 写了「代理可能回空 body，所以默认文案也得对」的理由并配了用例，同一理由没有施于 `rejected`。补齐后，任何一类的默认文案都被自己的类别钉死。

### 与 06.1-05 的边界：备份恢复 ≠ 恢复上一次快照

06.1-05 承接的是**平台恢复**（D1 备份与恢复流程、离线 JSON/SQLite 备份）。它**不**提供 `loadRecovery()` 意义上的「上一份快照」——那是提交时的单步回退，是一个不同的能力。

因此：06.1-05 完成后**不得**顺手把在线模式的「恢复上一次快照」按钮启用。除非确实提供了可取回的上一份快照，并且它由 `keepsRecoveryPoint` 如实声明。该约束已写进 **06.1-05 票据本身**与 **ADR-0002**，而不只留在本票。
