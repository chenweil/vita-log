### 逐条验收证据

**① PBKDF2-HMAC-SHA-256 / 210,000 次 / 独立盐 / 不依赖 Node crypto**
- `functions/_lib/password.ts` 全部走 `crypto.subtle`：PBKDF2-HMAC-SHA-256，迭代数取自凭据字符串，解析时强制 `>= 210,000`。
- 凭据编码为 `pbkdf2-sha256$210000$<saltHex>$<digestHex>`，盐 16 字节、摘要 32 字节，校验不依赖任何外部来源，因此 Secret 可以整体替换完成轮换。
- 证据：`tests/d1-password.test.ts`「固定使用 Web Crypto PBKDF2-HMAC-SHA-256 和 210,000 次迭代」「每个凭据使用独立盐」「凭据格式可往返」「损坏或被削弱的凭据一律 fail-closed」（22 个畸形凭据，含 `pbkdf2-sha256$1$…` 这种把 KDF 调低一档的输入）「不依赖 Node crypto」。

**② 30 分钟绝对过期 + 锁定/注销立即撤销**
- 会话是 D1 行而不是 Worker 全局：Pages Function isolate 是易失的，相邻两次请求不保证落在同一 isolate，内存会话会随机失效且无法跨 isolate 撤销。
- `openSession` 在登录时一次性写入 `expires_at = now + 30min`，此后任何请求都不续期——绝对过期而非滑动过期。
- D1 只存令牌的 SHA-256，不存令牌本身。
- 注销会顺带清理已过期行：`owner_session` 否则每次登录多留一行死数据，且没有任何其他代码会删。
- 撤销失败**不上报成功**：D1 不可达时行还在、会话在剩余 TTL 内仍然可用，回报「已注销」等于告诉本人编辑权没了而其实没有。改为 503。
- 证据：「会话 30 分钟后绝对过期，写入恢复为只读」（用 fake timers 在 8:29 仍可写、8:30:01 转 401，钉住「绝对」而非滑动）「注销立即撤销服务端会话」「注销时数据库故障不谎报已注销」「注销顺带清理已过期会话行」「D1 中只存会话令牌摘要」。

**③ Cookie 属性 + Origin/Host 强制校验 + 不开放 CORS**
- `sessionCookie` 固定 `HttpOnly; Secure; SameSite=Strict; Path=/api; Max-Age=1800`；`Path` 收窄到 API，静态资源请求不会带上它。
- `requireSameOrigin`：**起作用的判据是 `Origin`**——Cookie 由浏览器自动附带，服务端只能问浏览器请求来自哪里，而浏览器在写请求上必定如实回答；`Origin` **缺失即拒绝**，因为「没有证据」不等于「同源」。`Host` 必须存在且一致（**缺失也拒绝**，否则这个检查可能静默不执行），`Sec-Fetch-Site: cross-site` 一律拒绝。任一不满足即 403 `unauthorized`。
- 任何响应都不发 `Access-Control-Allow-*`；跨域客户端没有可协商的对象。
- 证据：「会话 Cookie 使用 HttpOnly、Secure、SameSite=Strict 且限时」「跨站写请求被拒绝，不发放 CORS 头」「缺失 Origin 与 Sec-Fetch-Site: cross-site 同样拒绝」「Host 不匹配或缺失时拒绝写入」。

**④ 账号/IP 双层限流 + 稳定错误码**
- 登录按账号和 IP 各计一个预算，窗口 60s、各 10 次；限流在 PBKDF2 **之前**判定，被限流的账号不再消耗迭代。登录成功会清空该账号与该 IP 的预算。
- 写请求按**会话令牌**和**来源地址**各限一次（60s/120 次）。只按会话限流的话，N 次登录就能拿到 N 倍预算；地址维度把同一来源的多次登录合并成一个预算。
- 错误码集合固定为 spec 的 5 个（`unauthorized`/`version-conflict`/`validation-failed`/`database-unavailable`/`migration-conflict`），路由无法发明第 6 个。
- 证据：「登录按 IP 限流，触发后即使密码正确也拒绝」「轮换来源 IP 不能绕过同一账号的限流预算」「同一地址的多次登录不能把写预算翻倍」「写接口按来源地址限流」「登录成功后清空失败计数，不会被自己的限流锁死」。

**⑤ 版本化写入 + 冲突保留未提交输入**
- 写入用 `UPDATE … SET payload=?, saved_at=?, **version=?** WHERE id=? AND version=?` 并读 `meta.changes`：0 行即冲突。判定在**单条语句内**完成，没有「先读后写」的窗口。
- **`SET` 里必须推进 `version`。** 只在 `WHERE` 里检查而不更新，会让库里版本恒定不变、后续每次写入都仍然匹配、冲突永远检测不到：两个页签会都存成功，其中一次编辑被静默抹掉。见下方审查记录。
- 冲突返回 409 `version-conflict`，文案「数据已更新，请重新加载；未提交输入已保留」；服务端不做任何部分写入。
- 空库单独区分：没有 `health_state` 行时返回 503「尚未导入健康数据」而不是版本冲突——日常保存不得悄悄创建在线事实来源，那是 06.1-03 迁移的职责。
- 客户端 `D1HealthRepository.commit()` 先读 `/api/session` 取版本再 PUT（公开投影刻意不含 `version`），被拒绝时仓库不丢弃任何本地状态。
- 证据：「保存真正推进 D1 里的版本：两个页签各持同一版本时只有一个能存」「正确密码登录后写入成功并推进版本」「过期版本返回稳定 version-conflict，且不覆盖已保存数据」「D1 不可用时 fail-closed」「非法快照载荷被拒绝且不落库」；`tests/d1-owner-client.test.ts`「写入前先取会话与版本」「版本冲突透传稳定错误码与服务端文案，保留未提交输入」。

### /code-review 结果与处理

双轴审查（Standards / Spec）派了一个只读子代理，固定点 `f50b805`。**结论是 do not ship**，抓到一个真缺陷：

| 发现 | 严重度 | 处理 |
| --- | --- | --- |
| `UPDATE` 的 `SET` 子句没有推进 `version`，只有 `WHERE` 在检查它。库里版本恒定不变，冲突永远检测不到：两个页签都存成功，一次编辑被静默抹掉。**测试替身在 JavaScript 里做了 `version + 1`，掩盖了这一点。** | HIGH | `SET` 加 `version = ?` 并绑定 `expectedVersion + 1`；新增「保存真正推进 D1 里的版本」用例（两个页签各持版本 4，只有一个能存）；把手写 fake 换成 `tests/support/sqlite-d1.ts`——**执行真实 SQL** 的 SQLite 替身，从根上消除这类漂移 |
| 客户端测试断言 `/api/login`、`/api/logout`，但 Cloudflare 只有 `functions/api/session.ts`；`FakeClient` 对任何 URL 都回放队列响应，于是「客户端和自己一致」被当成了「客户端和部署一致」 | HIGH | 新增 `functions/api/login.ts`、`functions/api/logout.ts`（与自托管 Node 服务同路径，一个客户端对接两种后端）；新增 `tests/deployment-routes.test.ts`，把适配器请求的每个 URL 和 `functions/api/*` 的实际文件列表对表 |
| 注销吞掉 D1 错误并返回「已注销」，而那一行还在、剩余 TTL 内仍可用——与验收第 2 条相反 | MEDIUM | `revokeSession` 改为抛出，路由映射为 503；新增「注销时数据库故障不谎报已注销」 |
| 写限流只按会话令牌，N 次登录即 N 倍预算，而票据第 4 条写的是账号/IP | LOW | 增加来源地址维度；新增「同一地址的多次登录不能把写预算翻倍」 |
| 「三个独立信号」是过度声称：边缘从同一个 Host 派生 `url.origin`，两者并不独立；且 `host !== null` 在 Host 缺失时**跳过**检查（fail-open） | LOW | 改为要求 Host 存在且一致（缺失即拒绝，检查不会静默不执行）；注释改成如实描述：`Origin` 是起作用的判据，Host 与 Sec-Fetch-Site 是纵深防御 |

复核后**不做**的：限流仍是 isolate 内内存计数（见下方边界说明，这是有意取舍且已如实记录）；WAF 层属部署配置，不在代码范围。

**这次审查本身就是「假绿」的一次实例**，和 06.1-01 记录的是同一类：断言全绿、产品是坏的，而替身比被测代码更「聪明」。区别在于这次替身在 JS 里替 SQL 做了决定性的一步（`version + 1`）。**教训：替身不得比被测对象多做任何计算。** 现在 `tests/support/sqlite-d1.ts` 直接执行生产代码里那条 SQL 字符串，替身与被测对象不可能再分叉；`functions/schema.sql` 也因此第一次被测试真正执行。

### 边界说明

- **未接入 `src/main.ts`**：本票不含 UI 接线，`06.1-04` 负责。`D1HealthRepository` + `ServerEditorAuth(client, now, { allowSetup: false })` 就是交给它接线的接口，且 `tests/deployment-routes.test.ts` 已保证它们请求的 URL 在 `functions/api/*` 里真实存在。第 ⑤ 项中「页面保留未提交输入」的**仓库层**已验证，**页面层**仍无验证。
- **凭据来源是部署 Secret，不是 D1**。`06.1-02b` 负责把初始化/重置收敛到 Secret 或一次性运维命令，并把 `/api/setup` 从公网彻底关闭；本票已经**不提供**任何公网 setup/注册/找回路由，所以 02b 不需要先拆掉什么。
- **限流是进程内的第二层**。Cloudflare Rate Limiting/WAF 是第一层、也是唯一跨 isolate 的那层；Worker 内的计数随 isolate 回收而清零。这是有意取舍：把计数写进 D1 会让每一次（尤其是攻击者想让它便宜的）登录尝试都产生一次数据库写入。两层同时生效，部署时必须确认 WAF 规则已配。
- **210,000 次 PBKDF2 在 Workers 免费套餐的 CPU 限额下可能超限**。这是部署前提，不是代码缺陷：`/wizard` 阶段需要确认套餐或调整迭代数，并在 Cloudflare 预览环境实测一次登录的真实耗时。
- **审计事件未实现**，归 `06.1-05`（时间/操作类型/结果/版本）。
- **迁移、备份、恢复未实现**，分别归 `06.1-03` / `06.1-05`；本票的 `PUT` 只处理日常保存，`POST`/`DELETE`/`PATCH` 一律 405。
- 未新增生产依赖；D1 类型仍是结构化声明，测试侧复用已在用的 `node:sqlite`。
- `npm run typecheck`、`npx vitest run`（126 passed / 20 files）、`npm run verify:release` 全部通过。
