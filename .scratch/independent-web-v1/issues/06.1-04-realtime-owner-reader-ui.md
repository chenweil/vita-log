# 06.1-04: 前端实时 owner/reader 集成

**What to build:** 让同一套页面在 Cloudflare 模式下默认以访客只读方式读取 D1；本人登录后可以编辑，保存后访客刷新读取最新数据。纯静态 `localStorage` 模式保持可查看和导出，但不再提供编辑入口。

**Blocked by:** 06.1-01, 06.1-02a, 06.1-02b

**Status:** done

- [x] Cloudflare 模式默认读取 D1，访客不需要登录即可看到完整看板和最新已保存数据。
- [x] 未登录、锁定和会话到期时隐藏/拒绝所有新增、编辑、删除、导入、清空、迁移、备份和恢复写路径。
- [x] 登录后开启 owner 编辑；保存成功后状态和页面数据更新，访客刷新可看到新快照。
- [x] 前端失败提示保留服务端错误码语义，不把数据库不可用当成空数据。
- [x] 纯静态模式不再启用源码内置编辑凭据，保留只读查看和导出/非写入能力。
- [x] 浏览器测试覆盖访客读取、登录编辑、锁定、会话到期、保存后刷新和直接事件/API绕过。

### 三个真实缺陷（本票修掉，非接线工作）

1. **登录后没有重载编辑快照，owner 首次保存必然被拒。** 匿名读到的是公共投影：没有 `version`、省略 owner-only 设置。旧代码登录成功只翻 `editing` 标志，编辑器停在一份**存不下去**的快照上。改为登录成功后经 `/api/owner-snapshot` 重载再开编辑器——**编辑能力由那次重载授予，不是由登录成功授予**。见 ADR-0002 的 06.1-04 段。
2. **编辑器会短暂停靠在旧投影上。** 重载期间若照旧渲染编辑器，那个窗口里输入的保存同样因无版本被拒。改为重载期间不渲染编辑器。
3. **访客被告知「数据只保存在当前浏览器」。** 在线模式与纯静态模式共用一个渲染器，存储卡片与页脚写死了本地措辞。访客据此会以为自己看的是本机数据，也无从知道刷新会变。按存储来源分流文案后，两种模式各说各的实话。

### 第二轮审查的四个缺陷（同样是真缺陷，不是接线工作）

第一轮的三条都只覆盖了「**一次**读取正确落地的路径」。下面四条都发生在**两次读取重叠**或**能力被凭空推断**的地方——上一轮的断言一次也没碰到它们。

4. **读取乱序会覆盖并保存 owner 设置（P1）。** 刷新按钮和登录表单在读取进行中同时可用，于是「匿名刷新」与「登录后重载」可以并发：公共投影晚到会覆盖页面上的快照，而仓库仍保留 owner 版本。下一次保存返回 **200**、版本 4→5，`primaryColor` 从 `#123456` 被改写成公共默认值 `#2F4A3C`——**一次成功的写入，静默清掉了 owner-only 设置**。修法两条独立防线：读取带序号，过期响应直接丢弃；`LoadResult.scope` 由仓库声明这份快照能不能写回，`canEdit()` 只对 `scope === 'owner'` 放行。
5. **登录成功但重载拿到 401，编辑器照开。** 旧代码只检查「快照非空」，而公共读取回退同样满足这个条件。编辑能力因此不再来自 owner 快照，而来自一个恰好为真的会话标志。
6. **会话撤销后重载，仍对公共投影开放编辑。** 服务端仍会拒绝写入，但用户已经能输入、输入无处可存。3 与 5 收敛到同一处判定：`load()` 内按 scope 决定，并显示「服务端没有返回完整编辑快照，页面保持只读。」——不解释的话，本人只会去找一个再也不会出现的登录框。
7. **D1 保存后错误启用恢复按钮。** `recoveryAvailable = recoveryAvailable || persistedSnapshot` 不问仓库有没有恢复点，于是在线模式保存一次就亮出「恢复上一次快照」，而 D1 根本没有该端点；旁边的「已清空全部记录，可从恢复点还原」也因此成为兑现不了的承诺。改为由仓库声明 `keepsRecoveryPoint`。

**为什么 4、5、6 是同一个病根**：页面把「持有会话」当成了「持有可写快照」。这两件事在只有一次读取时恰好相等，所以第一轮全绿；一旦读取重叠或会话在服务端先失效，它们就分叉了。

### 第三轮审查的两个缺陷：一个把响亮失败变成静默覆盖，一个是承诺没兑现

8. **过期读取仍在改写仓库的版本。** 第 4 项的修复只保护了页面：丢弃旧响应的同时，仓库已经按那次读取改写了 `version`。页面持有 v4 数据、仓库声称 v5，下一次保存以 v5 为基准被服务端接受，把 v4 的内容写成 v6 覆盖别的客户端的更新——**一个 200，没有冲突也没有报错**。复现：把一次 owner 读取压到服务端之外，等另一客户端把 D1 推到 v5 再放它过去。
9. **恢复承诺不符合实际能力。** 按钮禁用了，但清空/导入的确认框仍写着「当前数据会先保存到恢复点」，清空成功后仍显示「可清空全部记录，可从恢复点还原」。第二句出现在记录刚被清空之后，是本人最容易相信的一句话。**禁用按钮只挡住入口，挡不住这两句承诺。**

第三轮 P1 还带出一个**我自己引入的更坏形状**：仓库侧加上定序守卫之后，`restoreSqlite`（它绕过页面、直接调 `repository.load()`）那条路径从「响亮的 409」变成了「静默的 200」——仓库只推进自己的序号、页面不推进，于是途中那次刷新被页面采纳、仓库却保留恢复读到的版本，下一次保存以恢复后的版本为基准、用旧内容写回去。**修法不是再给仓库加一层，而是把第二条读取路径并回第一条**：`restoreSqlite` 改为调用页面的 `load()`。

### 逐条验收证据

**① 访客不登录即可看到完整看板和最新已保存数据**
`tests/d1-browser-integration.test.ts`「访客不登录即可看到完整看板和最新已保存数据」「访客看不到任何写入口，服务端一次写请求也没有收到」。读经 `/api/owner-snapshot`（无会话，401）→ `/api/snapshot` 公共投影，`runtime.requests` 断言这一对请求。页脚断言「数据保存在服务端，本页只读取」且**不含**「数据只保存在当前浏览器」。

**② 未登录/锁定/到期时隐藏并拒绝写路径**
- 未登录：15 个写入口选择器全部不存在，`runtime.requests` 无任何非 GET。
- 锁定：「锁定等服务端确认撤销后才变只读」断言 `POST /api/logout` 已发出**且 `owner_session` 行数为 0**——撤销发生在服务端，不是页面上藏起控件。
- 注销失败：「注销请求失败时不谎报已锁定」断言控件仍在、`owner_session` 仍为 1。
- 到期：「过了 30 分钟绝对期限后页面恢复只读」——只 fake `setInterval`（决定只读的那一个定时器），`setTimeout` 保持真实，否则 PBKDF2 会被冻住、用例因与到期无关的原因失败。
- **服务端中途撤销**（审查新增）：编辑中途收到 `unauthorized` 时页面停止提供编辑入口。这是新增行为：页面自己的时钟不是会话的唯一终点。
- **会话被撤销后刷新**（第二轮审查新增）：刷新回退到公共投影，编辑器关闭、写入口全撤，并说明原因。
- **绕过页面**：「匿名直接 PUT 被服务端拒绝」「匿名调用迁移与迁移预览同样被拒绝」——都经真实处理器返回 401 且 D1 不变。

**③ 登录后编辑、保存成功、访客刷新看到新快照**
「登录后重载完整编辑快照，保存成功且页面数据更新」断言 `GET /api/owner-snapshot` 发生在登录之后、编辑器随之打开、`storedVersion()` 由 4 变 5、页面显示新值且旧值仍在。
「访客刷新后读到本人刚保存的快照」用**第二个 runtime 共用同一个 D1**（两个浏览器），断言访客只走公开路由且读到新值。

**④ 前端失败提示保留服务端错误码语义，不把不可用当成空数据**
- 「D1 不可用时报服务不可用，不显示空看板，也不让访客去修本地存储」：断言无 `.metric-grid`、无「还没有记录」、且**不含**「本地存储」/「本地数据」。
- 「版本冲突时页面显示服务端原文，而不是通用的「保存失败」」（审查新增）：另一页签先存导致版本过期时，页面显示服务端原文「数据已更新，请重新加载；未提交输入已保留」，且不含通用文案、D1 未被写入。

**⑤ 纯静态模式只读、无凭据、保留查看与导出**
`tests/app.test.ts`「纯静态模式」四项：可查看可导出；无 `[data-action="auth-toggle"]`、无任何 form、四处锁定面板都说明这是只读页面、**不含**「进入编辑模式」；渲染本身不写存储（`RECOVERY_KEY` 仍为 null）；`LocalStorageHealthRepository` 本身**仍会写**——只读来自页面而不是被阉割的仓库。
`tests/bootstrap-closure.test.ts` 原有断言继续成立：静态分支仍只传两个参数、不含任何认证实现。

**⑥ 浏览器测试覆盖六种情形**
访客读取、登录编辑、锁定、会话到期、保存后刷新、直接 API 绕过，逐条对应上面各用例。第二轮再补 5 例、第三轮再补 4 例，全部落在「读取重叠 / 能力被凭空推断」上：重载期间不渲染编辑器、旧的公共响应晚到、登录成功但未取得 owner 快照、会话被撤销后刷新、D1 恢复点不谎称可用、清空/导入不承诺恢复点、过期读取不得改写仓库版本、SQLite 备份恢复与刷新读取的交错。

### 测试替身的设计（本票最要紧的一件事）

`tests/support/cloudflare-runtime.ts` **只当浏览器**：按 URL 路由到 `functions/api/*` 的真实处理器，跑真实 SQL，替身对授权、版本和数据不做任何决定。

**但它最初按 Cloudflare 的方式分发是错的**，审查用变异体证出来了：它只调用 `onRequest`，而 Cloudflare 优先调用方法级导出（`onRequestPut`/`onRequestPost`）。把 `onRequestPut` 换成不校验会话的实现后，本文件 11 个用例**全绿**。由于 `onRequest` 与 `onRequestPut` 目前调用同一个内部函数，这个错误当时不可见——正因如此它危险：将来给 `onRequestPut` 加了检查而 `onRequest` 没加，真实部署与测试就会分叉。已改为按平台规则优先方法级导出，复验：掏空 `onRequestPut` 现在转红。

替身保留两处浏览器行为，因为服务端依赖它们：Cookie 罐，以及同源写请求上的 `Origin`/`Host`（`requireSameOrigin` 缺少它们即拒绝，替身若不提供就只会测到生产环境不会走的分支）。

**三次「变异后仍绿」，前两次是被掩盖的缺陷，第三次是覆盖回归。**

前两次：见下段（`lockedHint` 恒真、顶栏忽略 `canUnlock`）。

第三次更重要——**第二轮修复自己引入的**。「重载期间不渲染编辑器」这条 ADR 契约在改完之后**一个断言都没有了**：删掉 `!reloadingForOwner &&`，全量 222 个用例仍然全绿（审查方与我各自独立跑过一遍）。原因是我把 `loginFinished` 从「等编辑器出现」改成「等读取结束」，恰好关掉了旧用例**偶然**探测那个窗口的时机，旧断言从此再也没能看见它。也就是说，一个 P1 修复让另一条既有契约静默失去保护，而绿得毫无破绽。补的用例走的是「锁定后重新登录」——此时页面手里那份 owner 快照仍然是 `scope: 'owner'`，唯一能压住编辑器的是重载本身，所以这条守卫重新变得可观测。

**这次没有用「删掉守卫」来消掉红灯**：`reloadingForOwner` 和 `snapshotScope` 在登录首次进入时确实覆盖同一个窗口，但两者并不等价——页面可能握着上一轮留下的 owner 快照（见上）。为了让这两条防线各有一个专属的红色断言，补测而不是合并。

**第三轮里有一个变异体本该转红却没有，因此被撤回**：把「恢复上一次快照」的确认框也改成按能力分流后，全量用例**依然全绿**。原因是那条路径在两种部署下都取不到分支——按钮只在 `loadRecovery` 真的答上来时才渲染，而能答上来的仓库必然留得下恢复点。这是一条任何可达状态都取不到的分支，属于没人会核对的承诺，已撤回并把理由写在代码旁。

**两次「变异后仍绿」都不是覆盖缺口，是被掩盖的缺陷**：`lockedHint` 恒真与顶栏忽略 `canUnlock` 起初都转绿——前者因为断言匹配的是数据面板的**另一句**文案，后者因为渲染后剥离 `auth-toggle` 的旧代码把两者都挡住了。前者补了逐面板计数断言；后者**删掉了渲染后剥离 DOM**这段补丁，改在渲染处按 `canUnlock` 门控，补丁消失后两处才各自可测。

### 测试替身里修掉的两个陷阱

1. **`tests/support/sqlite-d1.ts` 的 DDL 路径。** 原来写成 `new URL('../../functions/schema.sql', import.meta.url)`，Vite 会把这种内联形式**改写成开发服务器资源 URL**；在 jsdom 环境下基准变成 `http://localhost:3000/...`，`fileURLToPath` 报「The URL must be of scheme file」。node 环境的旧用例一直看不到，只有当 06.1-04 需要从 jsdom 引用这个模块时才暴露。已改用 `path.resolve` 构造。
2. **`new Request(request, { headers })` 会丢掉 body。** 替身最初这样转发请求体，写路由收到的永远是空载荷——一次真实的授权失败会看起来像校验失败。已改为显式取出 body 再构造。

### 边界说明

- **代码路径已验证，公网部署没有。** 本地跑的是真实 Pages Function 处理器 + 真实 SQL，覆盖的是代码；Cloudflare 预览/生产的匿名读取、未授权写入、会话失效、CSRF、限流、初始化与 D1 故障仍属 #06.1-06。
- **Cloudflare 产物必须用 `npm run build:cloudflare` 发布。** 用普通 `npm run build` 发布的产物没有 `d1` 标记，会退回只读纯静态模式——而访客看到的是一台空看板而不是错误。这是部署顺序问题，不是代码能单独保证的。
- **登录失败的提示仍不区分「密码错」与「服务不可用」。** `ServerEditorAuth.unlock` 返回 `boolean`，`/api/login` 返回 503 时页面会说「账号或密码错误」。这是 06.1-02a 定下的签名，改它要动共享契约与该票的用例；此处如实记录，不在本票改。
- **本票不提供 D1 的备份/恢复 UI。** `D1HealthRepository.loadRecovery()` 仍显式抛 `recovery-unavailable`，属 #06.1-05。在线模式下「恢复上一次快照」按钮因此恒为禁用——这条边界现在由 `keepsRecoveryPoint` 显式声明，而不是靠「D1 恰好加载不到恢复点」的巧合：页面过去在保存成功后凭 `persistedSnapshot` 直接点亮按钮，与仓库能力无关。
- **访客看不到记录明细列表。** 公共投影包含备注，但只读渲染不显示最近体重/围度/饮食列表（该列表只在编辑模式渲染）。这是本票之前就有的只读版式，未在本票扩大改动范围。
- 未新增依赖：未用任何新包；D1 类型仍由 `functions/_lib/d1-store.ts` 结构化声明。
- `npm run typecheck`、`npx vitest run`（228 passed / 25 files）、`npm run verify:release` 全部通过；另实测 `VITE_STORAGE_MODE=d1 vite build` 的产物含标记、普通构建不含。
