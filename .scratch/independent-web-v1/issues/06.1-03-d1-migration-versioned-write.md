# 06.1-03: D1 迁移与版本化写入

**What to build:** 让本人把本机 SQLite/JSON 快照迁移到空 D1，并以版本化完整快照执行日常写入；迁移和写入在冲突或失败时不静默覆盖数据。

**Blocked by:** 06.1-01, 06.1-02a, 06.1-02b

**Status:** done

- [x] D1 非空时拒绝自动迁移。
- [x] 迁移预览展示来源、各类型数量、总数、日期范围、营养汇总、设置摘要和 D1 是否为空。
- [x] 本人确认前不写入 D1；确认后完整导入并保留版本、时间戳和迁移结果。
- [x] 迁移写入复用 `06.1-02a` 已交付的版本化写路径；本票只负责迁移专有的空库保护、预览、对账与原子性，不重新实现日常保存。
- [x] 迁移失败、校验失败或数据库错误不改变当前 D1 快照。
- [x] 测试覆盖空库迁移、非空拒绝、重复迁移、版本冲突、对账和原子失败保护。

## 实现记录

**交付**：`functions/_lib/migration.ts`（预览摘要、空库保护、原子写入、对账）、
`functions/api/migrate.ts`（`POST /api/migrate`）、
`functions/api/migration-preview.ts`（`POST /api/migration-preview`）、
`tests/d1-migration.test.ts`（33 个用例）。

**先暂存、对账通过后才提升。** 候选行写入 `health_state_import`，在那里逐字节
对账，通过后再用带空库守卫的语句提升进 `health_state`。这是 ADR-0002「完成对账
和备份前不开放公网读取」能成立的前提：若直接写正式行再对账，被对账的就是访客正
在读的数据，比对失败时既不能回滚（删掉本人唯一一份健康数据比留下可疑数据更危
险），公网读取也已经打开了。暂存表是草稿位——失败时留着但不外露，重试覆盖它，
提升成功后清空；全仓库没有任何读取路径 SELECT 过它。

**提交边界是提升那条语句，其后不允许再抛错。** 校验与对账全部在提升之前完成；
提升之后只剩清空暂存表这类有界的草稿维护，失败被吞掉而不是报成迁移失败。

**因此「不改变当前 D1 快照」对 Cloudflare 有文档的迁移结果精确成立**：任何非 2xx
都发生在正式行存在之前，不存在半导入状态留给重试去踩。

| 失败点 | D1 当前快照 |
| --- | --- |
| 快照校验失败 / 预览过期 / 暂存写入失败 / 对账不一致 / 提升语句报错 / 空库守卫未命中（changes=0） | 完全未变，匿名读取仍为「尚未导入」，可直接重试 |
| 提升后的清理失败 | 已成功提交（200）。数据已上线且正确 |
| **D1 违反结果契约**：INSERT 执行了却不返回 `meta.changes` | **不确定**，可能已落库 |

第三行是明确划在保证之外的。Cloudflare 的 D1 结果契约要求 `meta.changes`，所以
这一状态按文档不应出现；一旦出现，代码无法在不越过提交点的前提下判定它是成功
还是失败——而越过提交点正是上一轮删掉最终回读的理由。两种可选做法都有害：重新
读一次会把提交点之后的代码请回来（就是刚被复审否掉的形状），直接当成功则可能
把一次根本没发生的导入报成成功。选择拒绝，并靠平台契约把这个状态挡在生产之外。

测试替身 `silentInsert` 已改成**先执行 INSERT 再隐去元数据**。原先那个版本直接
跳过写入，于是库里没有这行，表面上满足了上面的保证，实际上什么都没证明——这正是
本项目反复出现的「替身比被测对象少做一步 / 声称与证据不一致」。现在这个用例把
边界显式断言出来（`storedVersion() === 1`），而不是让它悄悄通过。

第二行是刻意如此。「提交之后再校验」只会制造死路：数据已经上线且正确，却告诉
本人导入失败，本人重试又被空库守卫以 409 拒绝——正是上一版踩的坑。所以提升后
的最终回读被**删除**而非保留：它校验的字节在提升前已经逐字节对过一遍，而它唯一
能捕获的两种情况（D1 写坏、提交后瞬时读失败）都无法通过回滚解决，前者不可撤销、
后者只会制造上面那个死路。暂存清理失败被吞掉是安全的：暂存行 `id=1` 且带 CHECK
约束、只用 `INSERT OR REPLACE` 写入，既不会累积也没有任何读取路径会 SELECT 它。

**「备份完成前不开放」尚未由本票覆盖。** 本票解决的是对账那半句；备份那半句依赖
部署顺序——迁移后先跑 06.1-05 的备份，再由 06.1-06 切到公网，中间不对外服务。
这一点写进 ADR-0002 的实现取舍，验收时按顺序核对。

**空库保护写在提升语句内部**（`WHERE NOT EXISTS`），而不是先 `SELECT` 再
`INSERT`：后者会留下窗口，并发的两次首次迁移都报成功而只剩一行——正是本票要防
的静默覆盖。空库判断用 `COUNT(*)` 而不是 `id = 1`。暂存写入**故意不带**守卫：
它是草稿位，失败后重试本就该覆盖它；守卫属于提升，不属于这里。

**复用 02a 的写路径。** 行内容由 `prepareVersionedState` 生成，与
`commitHealthState` 同一个函数，所以迁移行和日常保存行不可能形状不同；本票没有
重写日常保存，`PUT /api/snapshot` 仍然只能 UPDATE、依然无法创建这一行——这个
不对称正是「日常保存不会悄悄把迁移换成空快照」的根据。`version` 由语句绑定而
非写死 1，与对账比对的是同一个值。

**对账按字节比对，不只比数量。** 摘要是给本人预览看的批准依据，但数量、日期、
营养汇总全都相同时，一条被改写的备注、一个重排的字段仍是不同的数据——所以另外
逐字节比对 payload，并核对 version 与 saved_at。返回给本人的摘要由**被提升的那
批字节**重算，而不是复用请求里的快照。

**预览先规范化，再统计。** 未规范化的预览会照单全收「可遍历但语义非法」的快照
——`name: 12345`、`date: "not-a-date"`、字符串拼出的 `"0abc"` 营养值、被字典序
排反的日期区间——于是本人会看到一份**导入必定拒绝**的预览并为之确认。现在
`previewMigration` 先 `normalizeSnapshot`，两者不会对同一批数据给出不同答复。

**变异验证（非信任声明）。** 逐条植入、确认命中后再还原。提交边界一轮：把提升后
的清理改回抛错 → 转红；在提升后再插入一次会抛错的回读 → 转红。上一轮针对暂存
设计：把提升挪到对账之前（即复审第一轮指出的原设计）→ 5 个用例转红，其中包含
「匿名读取仍关闭」这条 ADR 断言；去掉暂存行的逐字节比对 → 3 个转红；跳过暂存
回读直接采信内存中的值 → 3 个转红；提升后不清空暂存表 → 1 个转红。

第二轮里「插入提升后回读」这条变异最初存活，原因是探针只拦了 statement 上的
`first`、没拦 `bind` 返回对象上的 `first`，于是那条回读走了未被污染的路径——这是
探针本身的漏洞，补齐后转红。同类的教训：**拦截器要覆盖被测代码可能走的每条
调用路径，否则「没被拦住」会被误读成「没发生」。**

前几轮：去掉 INSERT 的空库守卫 → 5 个用例转红；去掉 payload 逐字节比对 → 转红；
去掉 version / saved_at 对账 → 转红；容忍 `changes === undefined` → 转红；把
`prepareVersionedState` 换成裸 `JSON.stringify` → 2 个用例转红；去掉
`expectedVersion` 检查 → 转红；把 `COUNT(*)` 改成 `WHERE id = 1` → 转红；去掉
两处 405 分发 → 转红；分别去掉会话限流与地址限流 → 均转红。

早期几轮有三条变异存活，据此补了用例，其中一条暴露了生产代码里的死代码：摘要
比对在逐字节比对之后永远不会触发，已删除，返回摘要改为从库中字节重算。另有一条
限流变异存活：会话与地址预算同为 120 且无地址请求恒为 `unknown`，地址预算总是先
触发而遮住会话预算；补的用例轮换地址单独耗尽会话预算、按真实令牌清空会话桶单独
耗尽地址预算。

**复审发现并已修复（三轮共四处 P1）。** ① 初版先写正式行再对账，违反 ADR-0002
「完成对账前不开放公网读取」：复现为迁移返回 503 但匿名读取返回 200，且重试被
409 拒绝。② 改为暂存后，提升之后仍有「最终回读 + 清空暂存」，失败同样落在数据
已上线之后：复现为迁移返回 503、匿名读取 200、正式行已有数据。③④ 预览未规范
化、`expectedVersion` 经 `Number()` 转换放行畸形值。

②的根因是**我把「提交后再校验」当成了安全网**。它不是：它校验的字节在提交前已
经逐字节对过一遍，而它唯一能捕获的两种情况都无解——D1 写坏无法撤销，提交后瞬
时读失败只会把一次成功的导入报成失败并让人重试、再被 409 拒绝。正确的形状是
**提交点之后的任何失败都不能返回给调用方**。

另一层错误贯穿三轮：我在发现偏差时选择把它写进票据当作「已披露的例外」接受下
来。披露不等于解决，契约冲突应当改设计。根子在我只 `ls` 了 `docs/adr/` 就在实
现里断言符合 ADR-0002，而没读过它的第 22 行。

**顺带修正。** `guard` 从 `snapshot.ts` 提到 `_lib/api.ts` 共享（此前只有一处
调用，现两条路由共用），避免迁移与保存对「数据库不可用」给出不同状态码。
测试替身 `SqliteD1` 增加 `failOn`（只让某条语句失败）与 `silentInsert`（执行迁移
INSERT 但不返回变更数）两种行为——原先只有「整个 D1 报错」，那样用例会停在会话
查询上、根本走不到迁移代码，属于因错误的原因通过。暂存查询漏写 `?` 占位符
被这个替身当场抓住（真实 D1 同样会拒绝绑定数不符的语句）。路由白名单两处同步更新。

**未做（不在本票范围）**：重置/恢复路由归 06.1-05；迁移的前端入口归 06.1-04。
