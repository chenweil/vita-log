# 06.1-03: D1 迁移与版本化写入

**What to build:** 让本人把本机 SQLite/JSON 快照迁移到空 D1，并以版本化完整快照执行日常写入；迁移和写入在冲突或失败时不静默覆盖数据。

**Blocked by:** 06.1-01, 06.1-02a, 06.1-02b

**Status:** ready-for-agent

- [x] D1 非空时拒绝自动迁移。
- [x] 迁移预览展示来源、各类型数量、总数、日期范围、营养汇总、设置摘要和 D1 是否为空。
- [x] 本人确认前不写入 D1；确认后完整导入并保留版本、时间戳和迁移结果。
- [x] 迁移写入复用 `06.1-02a` 已交付的版本化写路径；本票只负责迁移专有的空库保护、预览、对账与原子性，不重新实现日常保存。
- [x] 迁移失败、校验失败或数据库错误不改变当前 D1 快照。
- [x] 测试覆盖空库迁移、非空拒绝、重复迁移、版本冲突、对账和原子失败保护。

## 实现记录

**交付**：`functions/_lib/migration.ts`（预览摘要、空库保护、原子写入、对账）、
`functions/api/migrate.ts`（`POST /api/migrate`）、
`functions/api/migration-preview.ts`（`POST /api/migration-preview`）、
`tests/d1-migration.test.ts`（33 个用例）。

**空库保护是同一条语句，不是先查后写。**
`MIGRATION_INSERT` 带 `WHERE NOT EXISTS (SELECT 1 FROM health_state)`。先 `SELECT`
再 `INSERT` 会留下一个窗口，并发的两次首次迁移都报成功而只剩一行——正是本票要防
的静默覆盖。守卫在 INSERT 内部，输掉竞争的一方拿到 0 行变更，转为
`migration-conflict`。同理，改用 `COUNT(*)` 而不是 `id = 1` 判断空库。

**复用 02a 的写路径。** 行内容由 `prepareVersionedState` 生成，与
`commitHealthState` 同一个函数，所以迁移行和日常保存行不可能形状不同；本票没有
重写日常保存，`PUT /api/snapshot` 仍然只能 UPDATE、依然无法创建这一行——这个
不对称正是「日常保存不会悄悄把迁移换成空快照」的根据。`version` 由语句绑定而
非写死 1，与对账比对的是同一个值，避免版本算法变更后只在落库之后才发现不一致。

**两类失败的 D1 状态不同，已分别验证并写明。**

| 失败点 | D1 是否改变 |
| --- | --- |
| 快照校验失败 / 非空库 / 预览过期 / 写入报错 | 完全未变 |
| 对账不一致（写入之后才发现） | 行已落库并对外提供 |

对账失败发生在 INSERT 之后，此时行已经在库里、公开读取路径已经在读它。这里
**不做回滚**：因为一次比对失败就删掉本人唯一一份健康数据，是更危险的结果。错误
如实写明「数据已写入 D1 并对外提供，请先查看当前数据再决定下一步」，而不是说
「未改动」。此后的迁移会被空库保护拒绝——这是正确的，重跑导入正是本票要防的覆盖。
本票不提供重置路由：它属于备份/恢复范围（06.1-05），而指向一个不存在的恢复流程
会让本人去找一个部署里没有的按钮。

**对账按字节比对，不只比数量。** 摘要是给本人预览看的批准依据，但数量、日期、
营养汇总全都相同时，一条被改写的备注、一个重排的字段仍是不同的数据——所以另外
逐字节比对 payload，并核对 version 与 saved_at。返回给本人的摘要由**库里的字
节**重算，而不是复用请求里的快照。

**预览先规范化，再统计。** 这一点是复审发现的真实缺陷：未规范化的预览会照单全收
「可遍历但语义非法」的快照——`name: 12345`、`date: "not-a-date"`、字符串拼出的
`"0abc"` 营养值、以及被字典序排反的日期区间——于是本人会看到一份**导入必定拒绝**
的预览并为之确认。现在 `previewMigration` 先 `normalizeSnapshot`，预览拒绝的与
导入拒绝的是同一份数据，两者不会对同一批数据给出不同答复。

**变异验证（非信任声明）。** 逐条植入、确认命中后再还原：去掉 INSERT 的空库守卫
→ 5 个用例转红；去掉 payload 逐字节比对 → 转红；去掉 version / saved_at 对账 →
转红；容忍 `changes === undefined` → 转红；把 `prepareVersionedState` 换成裸
`JSON.stringify` → 2 个用例转红；去掉 `expectedVersion` 检查 → 转红；把 `COUNT(*)`
改成 `WHERE id = 1` → 转红；去掉两个路由的 405 分发 → 转红；分别去掉会话限流与
地址限流 → 均转红。

第一轮有三条变异存活，据此补了用例后转绿，其中一条暴露了生产代码里的死代码：
摘要比对在逐字节比对之后永远不会触发，已删除，返回摘要改为从库中字节重算。
第二轮（复审后）曾有一条限流变异存活——会话与地址预算同为 120、无地址请求恒为
`unknown`，所以地址预算总是先触发，遮住了会话预算；补的用例轮换来源地址以单独
耗尽会话预算、并按真实令牌清空会话桶以单独耗尽地址预算，现在两条各自可证。

**顺带修正。** `guard` 从 `snapshot.ts` 提到 `_lib/api.ts` 共享（此前只有一处
调用，现两条路由共用），避免迁移与保存对「数据库不可用」给出不同状态码。
测试替身 `SqliteD1` 增加 `failOn`（只让某条语句失败）与 `silentInsert`（只让
迁移 INSERT 不返回变更数）两种行为——原先只有「整个 D1 报错」，那样用例会停在
会话查询上、根本走不到迁移代码，属于因错误的原因通过。路由白名单两处同步更新。

**未做（不在本票范围）**：重置/恢复路由归 06.1-05；迁移的前端入口归 06.1-04。
