# ADR-0002: Cloudflare D1 实时公开读取与服务端编辑授权

- 状态：已决定，实现中（#06.1-01 读取与公共投影、#06.1-02a 认证/会话/版本化写入、#06.1-03 迁移对账、#06.1-04 前端 owner/reader 集成、#06.1-05 备份恢复和审计代码已交付；平台恢复、定时任务及公网验收待目标环境取证）。2026-10-09 修订：PBKDF2 迭代数 210,000 → 100,000，因 Cloudflare 生产运行时硬校验拒绝超过 100,000 的迭代数，详见「实现取舍（#06.1-06 补充）」。
- 日期：2026-10-05
- 关联：#06.1

## 背景

原 #06 完成的是手动生成 JSON 的静态只读快照。新的访问模型要求所有访客看到服务端当前已保存数据，只有本人通过密码登录后才能编辑。公网部署优先使用 Cloudflare。

## 决策

- 保留 Vite 静态前端，部署到 Cloudflare Pages；动态 API 使用同源 Pages Functions，在线事实来源使用 Cloudflare D1。
- D1 是唯一在线事实来源。本机 SQLite 迁移完成后仅保留为离线备份/恢复副本，不双写、不做在线镜像。
- 未登录访客可以读取完整健康看板：昵称、体重/体脂、围度、步数、打卡、饮食明细和备注。认证、会话、备份和内部元数据不进入公开响应。
- 未登录状态始终只读。本人通过服务端密码会话后才允许写入；新增、修改、删除、导入、清空、迁移、备份和恢复都由服务端逐请求授权。
- 首个管理员通过部署时 Cloudflare Secret 或一次性运维命令预置，公网不开放初始化接口。密码遗失只通过 Cloudflare Secret/运维命令离线重置。
- Worker 使用 Web Crypto PBKDF2-HMAC-SHA-256、100,000 次迭代和独立盐。会话 30 分钟绝对过期，锁定/注销立即撤销。
- 会话 Cookie 使用 `HttpOnly`、`Secure`、`SameSite=Strict`；写请求强制校验 `Origin/Host`，不开放 CORS。
- 登录和写接口使用 Cloudflare Rate Limiting/WAF 与 Worker 内部按账号/IP 双层限流。写操作只保留时间、操作类型、结果和版本等最小审计事件。
- 健康数据 API 使用 `Cache-Control: no-store`。本人保存成功后，访客下一次刷新读取 D1 最新快照，不做主动推送。
- D1 必须为空才能首次迁移。本机 SQLite 先生成迁移预览，核对数量、类型、日期、汇总和设置摘要，由本人确认后一次性导入；完成对账和备份前不开放公网读取。
- D1 使用平台恢复能力，定期导出完整 JSON 到受限离线备份，同时保留本机 SQLite。D1/Pages Functions 故障时 fail-closed，访客看到明确不可用提示，不回退旧缓存、本机数据或空数据。
- #06 的手动只读 JSON 快照继续保留，但单独标注为非实时分享。

## 取舍

Cloudflare Pages + Pages Functions + D1 与公网访问路径同源，避免独立 API 域名和 CORS 凭据面；D1 迁移牺牲本机 SQLite 作为在线主库的简单性，换取 Cloudflare 上可用的服务端事实来源和实时读取。完整看板公开是产品决策，安全边界由服务端写入授权、初始化保护、会话、限流、CSRF 和 fail-closed 读取共同承担。

### 实现取舍（#06.1-02a 补充）

- **会话存 D1，不存 Worker 全局。** Pages Function isolate 是易失的，相邻两次请求不保证落在同一 isolate。内存会话会随机失效，且无法跨 isolate 撤销。30 分钟绝对过期和注销立即撤销因此都是「那一行」的性质。
- **D1 只存会话令牌的 SHA-256。** 从 D1 里捞出一行不等于拿到可用 Cookie。
- **版本化写入靠 `WHERE version = ?` + `meta.changes`**，判定在单条语句内完成，没有先读后写的窗口。空库单独报告为「尚未导入」，日常保存不得创建在线事实来源。
- **限流分两层**：Cloudflare Rate Limiting/WAF 是唯一跨 isolate 的第一层，Worker 内的账号/IP 计数是第二层。Worker 内计数不写 D1——否则每一次（尤其是攻击者想让它便宜的）登录尝试都会产生一次数据库写入。
- **写接口的「账号」维度即会话维度。** 上面的「按账号/IP 双层限流」在登录接口上字面成立（按用户名 + 按地址各计一次）。写接口只有一个身份——唯一管理员本人——而一次写必须持有一个会话，所以可写的「账号」在物理上就等于那个会话：再加一层按用户名的全局计数，与地址计数相比只会更粗，不会多挡住任何东西，却会让本人在两台设备上同时使用时更早触发上限。因此写接口按**会话 + 来源地址**两维限流：会话维度防止单个编辑器刷写，地址维度防止同一来源的多次登录把预算翻倍。这是对原决策在单用户约束下的等价收敛，不是削弱。
- **锁定与注销必须由服务端确认。** 客户端隐藏控件不等于撤销会话：Cookie 的寿命长于那次调用，所以注销失败时页面若照常显示「已锁定」，就是在告诉本人已经安全而其实没有。因此客户端等到服务端确认撤销后才置为只读；失败时保持可编辑状态，如实反映会话仍然有效。
- **凭据来自部署 Secret。** 编码为 `pbkdf2-sha256$<iterations>$<salt>$<digest>`，盐、迭代数、摘要都在串里，校验不读外部来源，因此轮换＝换掉整个 Secret。
- **公开投影刻意不含 `version`**（内部存储元数据）。编辑客户端从会话保护的 `GET /api/owner-snapshot` 一次读取完整 `HealthSnapshot` 与该行版本（单条 `SELECT payload, version`），保存时使用这次读取或上次成功保存的版本。`/api/session` 仅用于客户端登录态检查，其版本字段不能用于刷新旧输入的 `expectedVersion`。匿名投影省略 owner-only 设置，不能直接保存；登录后必须重新加载完整编辑快照。

### 实现取舍（#06.1-03 补充）

- **首次迁移先暂存、对账通过后才提升。** 「完成对账前不开放公网读取」只有把候选数据放在读取路径够不到的地方才成立：候选行先写入 `health_state_import`，在那里逐字节对账，通过后再用一条带空库守卫的语句提升进 `health_state`。如果直接写入正式行再对账，被对账的就是访客正在读的数据——比对失败时既无法回滚（删除本人唯一一份健康数据比留下可疑数据更危险），公网读取也已经打开了。暂存表是草稿位：失败时留在那里但不外露，重试直接覆盖，提升成功后清空。全仓库没有任何读取路径 SELECT 过它。
- **提交边界是提升那条语句，其后不允许再抛错。** 校验与对账全部在提升之前完成；提升之后只剩清空暂存表这类有界的草稿维护，失败必须被吞掉而不是报成迁移失败。理由是「提交后再校验」只会制造死路：数据已经上线且正确，却告诉本人导入失败，本人重试又被空库守卫以 409 拒绝。由此「迁移返回的任何错误都发生在正式行存在之前」这条性质可以精确成立，而不是近似成立。
- **空库守卫在提升语句内部**（`WHERE NOT EXISTS`），不是先查后写：后者会留下窗口，并发的两次首次迁移都报成功而只剩一行。空库判断用 `COUNT(*)` 而非 `id = 1`。
- **对账按字节比对 payload 并核对 version/saved_at**，不只比数量：数量、日期、营养汇总全相同时，被改写的备注仍是不同的数据。返回给本人的摘要由库中字节重算。
- **公开读取前的备份尚未在本票覆盖。** 本票解决的是「对账完成前不开放」；「备份完成后才开放」依赖部署顺序——迁移后先跑 06.1-05 的备份，再由 06.1-06 切换到公网，中间不对外服务。代码层面无法单独保证后半句，验收时需要按这个顺序核对。

### 实现取舍（#06.1-04 补充）

- **部署模式由构建期标记声明，不由运行时探测决定。** 标记沿用自托管服务的同一个 `<meta name="vita-log-storage" content="…">`：Node 服务在响应 `index.html` 时注入 `sqlite`，Cloudflare Pages 没有这一步，因此由 `VITE_STORAGE_MODE=d1` 在构建时注入。**不在运行时探测 `/api/*` 是否存在**——那会把「没有部署在线服务」和「服务临时不可用」混为一谈，探测失败就回退 localStorage 的页面会给每个访客一台看起来健康的空看板，正是本 ADR 要求 fail-closed 的那种静默降级。未设置该变量时不注入任何标记，纯静态构建因此保持只读。
- **标记拼错必须退回只读，而不是半连接。** 只有精确等于 `d1` 才注入；`D1`、`d1 ` 之类的近似拼写一律不注入。`tests/deployment-modes.test.ts` 把「构建注入什么」与「main.ts 认什么」钉在同一处，两边不一致即红。
- **登录后必须重载完整编辑快照，编辑能力由那次重载授予。** 匿名读到的是公共投影：没有版本、且省略 owner-only 设置。直接翻 `editing` 标志会让编辑器停在一份**存不下去**的快照上——首次保存必然因无版本被拒，或静默丢掉未投影的设置。因此登录成功后先经会话保护的 `/api/owner-snapshot` 重载，再开编辑器；重载期间不渲染编辑器，否则会短暂停靠在旧投影上，那个窗口里输入的保存同样会被拒。登录成功本身不是授权，**服务端返回的完整快照才是**。
- **编辑能力绑定在快照上，不是绑定在会话上。** `LoadResult` 由仓库声明 `scope`（`owner` / `projection`），页面只对 `owner` 放行编辑。会话有效与「手里这份快照可写」只有在单次读取时才恰好相等，读取一重叠或服务端先撤销会话，两者就分叉。把会话标志当授权会产生两种假绿：旧公共响应晚到时编辑器停在访客那份投影上，而下一次保存会 **200**、把 owner-only 设置静默改写成公共默认值；登录后重载拿到 401 时编辑器照开。
- **读取带序号，过期响应直接丢弃；页面与仓库必须用同一条规则。** 刷新按钮与登录表单在读取进行中同时可用，「匿名刷新」与「登录后重载」可以并发，后发的不一定是先答的——一次发得更早的请求完全可能观察到更新的服务端状态。晚到的旧响应不仅会覆盖页面快照，连带把它的恢复点探测结果一起带回来，因此页面侧的序号判定同时覆盖两者。
  另一半在仓库侧，且判定标准是**最新发起**的那次读取，而不是最后落地的那次。页面丢弃旧响应时，仓库若已按那次读取改写了版本，页面手上是 v4、仓库却声称 v5，于是下一次保存以 v5 为基准被服务端接受，把 v4 的内容写成 v6 覆盖别的客户端的更新——一个 200，没有冲突也没有报错。**只在页面加序号是不够的**：`D1HealthRepository` 与 `SqliteHealthRepository` 各自维护同一套定序，仓库版本必须始终等于页面当前持有的那份快照的版本。
- **服务端说会话没了，页面就停止提供编辑入口。** 页面自己的时钟不是会话的唯一终点：本人可以在另一台设备锁定，或服务端直接丢弃会话行。编辑中途收到 `unauthorized` 时，页面据此转只读，而不是继续显示一个每次保存都会被拒的编辑器。安全边界始终在服务端，这里只是让页面不再谎称自己能写。重新登录会清掉该状态。
- **「重载期间不渲染编辑器」要单独测，不能靠 `scope` 顺带覆盖。** 页面可能握着上一轮留下的 owner 快照（锁定后重新登录即是），此时 `scope` 仍为 `owner`，唯一压住编辑器的就是重载本身。首版这条断言压在「等编辑器出现」的等待谓词上；重载改成「等读取结束」后那个窗口再无人观测，守卫一度可以在删掉后全绿。现在由「锁定后重新登录」用例直接钉住。
- **恢复入口与恢复承诺都按能力说话。** `HealthDataRepository.keepsRecoveryPoint` 说明 `commit` 是否真的留下 `loadRecovery` 能取回的上一步。D1 尚未部署恢复端点（属 #06.1-05），因此在线模式既不点亮「恢复上一次快照」，也不在清空/导入的确认框与结果文案里承诺恢复点——尤其「已清空全部记录，可从恢复点还原」出现在记录刚被清空之后，是本人最容易相信的一句话。禁用按钮只挡住入口，挡不住这两句承诺。**该声明不因 #06.1-05 交付而自动变为真**：平台恢复与离线备份提供的是备份/恢复流程，不是提交时的单步回退；要启用该按钮，必须确实存在可取回的上一份快照，并由该字段声明为 `true`。
- **登录失败必须区分四类，因为它们的修复动作相反。** `EditorAuth.unlock()` 返回可辨析结果而非 `boolean`：凭据被拒、被限流、服务不可用各带自己的文案。旧契约把三者压成同一个 `false`，页面一律显示「账号或密码错误」——于是 503（本人该稍后重试）与 401（本人该检查密码）给出相反的指令，而网络失败这种**根本没有信息**的情况被报成了一条确定的坏消息。分类依据是 **HTTP 状态**：两个后端在限流时都返回 `code: 'unauthorized'`，与密码错误同码，按 body 分类会把限流并回凭据错误。服务端原文优先于客户端默认文案——只有当服务端没给 message 时（代理/WAF 可能回空 body），默认文案才上场，而那时它必须属于正确的类别。
- **只读是「这份部署能不能编辑」，不是「此刻有没有解锁」。** 纯静态构建没有服务端可以授权写入，因此它既不显示「进入编辑」，也不显示「验证本人身份后可以新增…」——那是一条走不通的路线。两者语义不同，故 `EditorAuth.canUnlock()` 与 `isUnlocked()` 分开：前者是部署属性，后者是会话状态。
- **同一套渲染器按存储来源选文案，而不是把措辞写死。** 在线模式下把 D1 故障说成「本地数据读取失败」会把访客送去修浏览器存储，而故障根本不在那里；反过来，纯静态构建说「数据保存在服务端」同样是假的。访客看到的「数据保存在服务端，本页只读取」与纯静态版的「数据只保存在当前浏览器」互为对照，两条都有行为级断言。

## 验收边界

### 实现取舍（#06.1-05）

- 完整备份通过本人会话保护的 API 导出到受限离线目录，同时生成兼容现有工具的 SQLite 副本；不新增云对象存储，不把离线副本当在线镜像。
- 应用恢复通过版本化覆盖完成，保留递增版本；运维客户端先持久化当前在线 JSON/SQLite，失败则不发恢复请求。服务端无法观察本机文件系统，直接调用恢复 API 的本人负责先保留副本；请求仍独立验证会话、同源、限流和预期版本。
- 健康写入与最小审计在 D1 batch 事务中提交。审计只记录时间、操作类型、结果、版本，不复制健康快照；整库不可用时不能保证将失败写回同一库，平台运行日志另行取证。
- 审计在写语句之后根据实际变更和行内容判定，不能将准入当成功；无法确认记 unknown，空库记 not-initialized。元数据缺失导致客户端收到 503 不代表事务没有落库，已被事务证明的提交仍可记 success。新增结果通过增量迁移承接，旧记录原样保留。
- 写入与导出审计分别保留最近 10,000 / 1,000 条，在追加事务内清理超额元数据，并提供分类游标分页；备份/导出另设每会话、每 IP 每分钟 30 次预算，不占用保存额度。导出 429 不撤销或误关闭有效编辑会话。
- Time Travel 留在 Cloudflare 运维权限边界。恢复整库后撤销恢复出来的会话、重验 schema 和数据，再重新开放访问。恢复操作、周期任务及公网取证属 #06.1-06；流程见 `docs/d1-backup-recovery.md`。

上述决定只完成设计收敛，不代表公网部署已经安全通过。实现后必须在 Cloudflare 预览和生产环境验证匿名读取、未授权写入、会话过期/注销、初始化抢占、CSRF、限流、D1 迁移对账、备份恢复和故障 fail-closed。

#06.1-04 的浏览器级验收已在本地用真实 Pages Function 处理器 + 真实 SQL 完成（`tests/d1-browser-integration.test.ts`），但**这只覆盖代码路径**。Cloudflare 构建必须以 `npm run build:cloudflare` 发布——用普通 `npm run build` 发布的产物没有 `d1` 标记，会退回只读纯静态模式，而访客看到的是一台空看板而不是错误。切换到公网属 #06.1-06。

### 实现取舍（#06.1-06 补充）

- **迭代数从 210,000 降到 100,000，是被平台上限逼出来的，不是调优。** Cloudflare 的**生产**运行时对 PBKDF2 有硬校验：超过 100,000 次迭代时不执行派生，直接抛 `NotSupportedError: Pbkdf2 failed: iteration counts above 100000 are not supported`。这是输入校验而不是 CPU 预算，**任何套餐都一样**，所以「升级到 Workers Paid」解决不了它——本项此前被误判为「免费套餐 CPU 限额可能超限」，那个框架是错的：失败与耗时无关，超限时根本不进入计算。
- **本地对这类问题必然假绿，所以护栏放在解析层。** workerd 自身可配置该上限、本地构建默认不施加，Node 也不施加，于是整个本地套件在 210,000 下全绿、每次真实部署的登录却都失败。现在 `PLATFORM_MAX_PBKDF2_ITERATIONS` 取**生产**值（不是 workerd 的常量），`parseCredential` 与 `derivePassword` 都在本地拒绝超限输入，把「平台在请求时拒绝」变成「本机确定性拒绝」；另有一条断言钉住部署成本不超过该上限。
- **显式接受：部署成本低于 OWASP 推荐。** 本部署跑 100,000 次，OWASP 对 PBKDF2-HMAC-SHA-256 的当前推荐是 600,000。这个缺口被**有意接受**：平台没有提供达到它的途径（原生 Web Crypto 受入口校验约束，WASM 实现计入 CPU 且需要付费套餐），补偿控制是**口令熵**（见下条）与在线限流。重新评估条件一并写死：平台一旦放开上限，目标值是 **600,000**——把迭代数调回 210,000 并不等于合规，那只是把一个本来就不达标的值调回来。
- **事实更正：原决策的 210,000 引错了行。** 那是 OWASP 给 **PBKDF2-HMAC-SHA512** 的数字，而代码里是 `hash: 'SHA-256'`，对应 600,000；同一迭代数下 SHA-256 每轮成本更低，所以这个配对错误使实际成本低于原决策以为的水平。它不是一条「接受」，是对原决策的事实性更正——接受理由与补偿控制都和上一条不同，因此分开记，避免将来把「调回 210,000」误读成回到推荐值。
- **补偿控制是密码熵，不是 pepper。** 曾考虑加入服务器端 pepper，随后否决：密码摘要只存在于 Cloudflare Secret（D1 中没有任何凭据表），pepper 也只能放在同一类存储里，能读到一个就能读到另一个——它防不住它本该防的「拖库」场景，却要多一个能让本人被锁在门外的必填 Secret，且轮换时全部凭据同时失效。真正有指数级收益的是熵，所以创建凭据的门槛从 12 提到 20 字符并拒绝明显低熵串与常见弱口令（`server/credential-policy.ts`），**CLI 与部署向导共用同一条规则**，避免两份拷贝各自漂移。在线爆破由既有限流挡住（按账号 + 按来源地址，均在 KDF 之前判定）。
- **密码门槛只在创建凭据时生效，不在登录时。** 早于该规则创建的凭据必须仍能登录；在门口抬高门槛是把本人锁在外面，不是保护什么。
- **凭据不可用必须如实报错，不能伪装成密码错误或暂时故障。** 平台拒绝、Secret 缺失、格式或迭代数越界——这三件事都会让每一次登录失败，且与提交的密码无关，所以它们都不是「凭据被拒」；但它们同样**不是**暂时故障：并进「健康数据服务暂时不可用，请稍后重试」会让本人去查 D1/WAF/Access（缺陷在 Secret），而「稍后重试」永远不会成功。实现把它们统一为 `CredentialUnusableError`，登录路由返回 503 与指向修复动作的文案。
- **这是对 `owner-credentials.ts` 原有「一切失败都折叠成 false」的一处有意修改。** 折叠仍保留在「猜错用户名 / 猜错密码」之间——那才是枚举风险；放开的是「部署根本无法校验任何人」这一类。代价是未认证调用方可以读到一个比特的部署状态（本部署的凭据不可用）；收益是本人不会拿着「密码错误」去修一个没坏的东西——而这一类的自我修复动作全部指向错误方向（换密码、重开会话、重启服务）。
- **错误码仍留在五码封闭集合内。** 客户端从错误码只需要读出「服务坏了，不是密码错」这一类别，因此复用 `database-unavailable`；具体原因（迭代数、上限、缺失的是哪个 Secret）只进平台日志，不返回给未认证调用方。
- **凭据在部署前就校验。** CLI 生成之后、向导写入 Secret 之前都调用同一个校验函数，拒绝生成平台无法校验的凭据——否则「部署完成」与「站点被锁死」会同时发生，而登录接口无法告诉本人是哪一种。

### 待评估（#06.1-06 记录，未决定）

**回到 OWASP 推荐值的唯一现实路径，是绕开 `crypto.subtle` 的 PBKDF2 入口校验、用纯 JS/WASM 自己实现 KDF。** 不是「把 KDF 拆到独立 Worker」：那个上限是运行时对 API 入参的校验（workerd 的 `checkPbkdfIterations`），同一运行时内的任何 Worker、任何套餐都一样；`nodejs_compat` 下的 `node:crypto` 派生走的是同一处检查。独立 Worker 只改变 CPU 预算，改变不了这个校验——把它记成出路会误导下一次评估。

候选与代价，供将来评估时对照：

- **Argon2id（WASM）**：内存困难，比继续抬高 PBKDF2 轮数更能抵抗 GPU/ASIC 离线爆破；workerd 维护者公开确认此路可行。代价：WASM 计算全额计入 CPU，基本需要 Workers Paid；包体增大；引入第三方实现需要供应链审查；凭据格式改变，所有已部署 Secret 必须重新生成。
- **PBKDF2（WASM，保持现有凭据格式）**：格式兼容、迁移成本最低，但本质仍是 PBKDF2——把轮数抬到 600,000 只是回到推荐值，没有解决 PBKDF2 本身易被 GPU 加速的问题。

触发重新评估的条件（满足其一即可重启，否则维持现状）：平台提高迭代数上限；因故需要整体轮换凭据；安全审查要求内存困难型 KDF。
